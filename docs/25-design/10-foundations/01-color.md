# 색

## 팔레트 선택

| 갈래 | 색 | 이유 |
| --- | --- | --- |
| **Brand** | teal | 차분하고 신뢰감 있는 계열. 불안한 상황에서 읽는 서비스라 채도 높은 색을 피했다 ([원칙 1](../01-principles.md)) |
| **Neutral** | 약간 차가운 회색 | teal과 온도가 맞는다 |
| **Status** | emerald / amber / red / blue | 의미가 관습적으로 고정된 색. 브랜드가 바뀌어도 이건 바뀌지 않는다 |

brand와 status 스케일은 검증된 공개 스케일을 기반으로 했다.
색을 새로 만드는 것보다 **대비가 이미 예측 가능한 스케일을 쓰고 검증하는 쪽**이 안전하다.

## 대비 검증

전 조합을 계산해서 확인했다. 눈으로 고르지 않았다.

- 텍스트: **WCAG AA 4.5:1** 이상
- 비텍스트(입력 테두리·포커스링): **3:1** 이상
- 라이트/다크 **양쪽** 모두

### 검증 과정에서 바꾼 값

측정하지 않았다면 넘어갔을 것들이다.

| 항목 | 문제 | 조치 |
| --- | --- | --- |
| 버튼 채움 | `brand-600`에 흰 글자 = **3.74** (미달) | 채움을 `brand-700`로 한 단계 내렸다 |
| 다크 `fg-subtle` | `neutral-500` = **3.67** (미달) | `#85858e` 전용 단계를 추가 |
| 라이트 `fg-subtle` | sunken 배경 위 **4.40** (미달) | `#6b6b73` 전용 단계를 추가 |
| 입력 테두리 | `neutral-300` = **1.48** (미달) | `#8b8b94` 전용 단계를 추가 |

> 팔레트에 `450`, `550`, `750` 같은 **비표준 단계**가 있는 이유가 이것이다.
> 밝기 순서가 아니라 **대비 요구를 맞추려고 끼워 넣은 단계**다.

### 재검증 — 스크립트로 돌린다

색 토큰을 바꾸면 **반드시** 다시 측정한다. 눈으로 판단하지 않는다.

```bash
cd FE && npm run check:contrast      # 64개 조합, 실패 시 exit 1
VERBOSE=1 npm run check:contrast     # 전체 측정값 출력
```

스크립트(`FE/scripts/check-contrast.mjs`)가 `globals.css`의 팔레트를 **직접 파싱**하므로
문서에 적힌 값과 코드가 어긋날 수 없다. 검사 목록은 semantic 매핑과 같아야 하며,
한쪽만 바꾸면 스크립트가 잡는다.

상대휘도는 WCAG 2.x 정의를 그대로 쓴다:

```
L = 0.2126·R + 0.7152·G + 0.0722·B     (각 채널은 sRGB 역감마 적용 후)
ratio = (L밝은 + 0.05) / (L어두운 + 0.05)
```

> CI에 붙일 수 있다(실패 시 종료 코드 1). 넣을지는
> [열린 질문](../10-foundations/07-accessibility.md#미도입).

## 다크 모드

`.dark` 클래스 전략(media 쿼리 아님)이라 사용자가 라이트/다크/시스템을 **직접 고를 수 있다.**

다크는 라이트를 단순히 반전한 것이 아니다:

- **표면**: 라이트는 raised가 더 어둡고, 다크는 더 밝다. 층은 밝기 차로 만든다
- **그림자**: 다크에서는 거의 보이지 않는다. 층 표현을 표면 밝기에 맡긴다
- **브랜드**: 링크는 밝게(`brand-300`), 버튼 채움은 밝은 색 + 어두운 글자로 뒤집는다
- **상태색**: 어두운 배경에서는 `-400` 계열을 쓴다. `-700`은 다크에서 읽히지 않는다

## 하지 말 것

- 컴포넌트에서 primitive 직접 사용 (`bg-teal-700`) → [토큰 규칙](../02-tokens.md)
- 색만으로 정보 전달 → 아이콘/텍스트 동반
- `fg-subtle`보다 흐린 텍스트 → 이미 AA 최소선이다
- 임의의 hex 값 → 팔레트에 없으면 팔레트에 먼저 추가한다
