# 인증

## 방식

**소셜 로그인 + JWT.** 자체 비밀번호를 만들지 않는다 — 비밀번호를 보관하지 않으면
유출 리스크와 재설정 흐름이 통째로 사라진다.

```
FE ──► GET /auth/{provider}         BE가 제공자로 리다이렉트
       ◄── 제공자 콜백 ──► BE       인가 코드 → 토큰 → 프로필
FE ◄── /auth/callback#token=<jwt>   fragment 로 전달 (서버 로그에 안 남는다)
```

토큰은 FE의 `lib/auth-token.ts`가 보관하고, axios 요청 인터셉터가 `Bearer`로 첨부한다.

## 제공자 우선순위

| 제공자 | 우선 | 이유 |
| --- | --- | --- |
| **Google** | 1 | 타깃이 외국인이다. 국내 소셜은 가입 자체가 장벽일 수 있다 |
| Apple | 2 | iOS 사용자 비중, 개인정보 보호 선호 |
| Kakao / Naver | 3 | 한국인 사용자를 받게 되면 필요 |

→ 국내 소셜을 1순위로 두지 않는 것이 이 서비스의 특징이다.

## 계정 모델

한 `User`에 여러 `AuthIdentity`를 붙인다. 같은 사람이 구글/애플로 각각 가입해
계정이 갈라지는 문제를 나중에 병합할 수 있게 하기 위해서다.

> 이메일이 같다고 **자동 병합하지 않는다.** 제공자 이메일이 검증되었다는 보장이 없다.

## 권한

`role: USER | ADMIN` 두 단계로 시작한다.
모더레이터 역할은 [모더레이션](../20-product/10-features/07-moderation-and-reporting.md)의
운영 형태가 정해진 뒤에 추가한다.

## 보안 메모

- OAuth `state`를 CSRF 방어에 쓴다. **콜백 오리진과 로그인 시작 오리진이 같아야** 한다
  (다르면 state 쿠키가 실려오지 않아 모든 로그인이 실패한다)
- 토큰은 URL query가 아니라 **fragment**로 전달한다 (fragment는 서버로 전송되지 않는다)
- 제공자 자격증명이 없으면 해당 라우트만 닫히고 **앱 전체는 정상 부팅**해야 한다
  (로컬/테스트에서 자격증명 없이 개발 가능해야 한다)

## 열린 질문

- 토큰 저장 위치: localStorage vs httpOnly 쿠키. 후자가 XSS에 강하지만 CSRF 대응이 필요하다
- 리프레시 토큰을 둘 것인가? (없으면 만료 시 재로그인)
- 계정 삭제 시 작성 글을 어떻게 처리할 것인가? (익명화 vs 삭제 — 검색 자산과 충돌)
