# ADR-0003 · 영어를 1급 언어로 두고 다국어로 확장한다

- **상태**: 수락됨 — 단, **"MVP 는 영어 단일" 부분은 [ADR-0005](./0005-multilingual-from-day-one.md)가 대체한다**
- **날짜**: 2026-08-24

## 맥락

konnect의 사용자는 **한국에 있는 외국인**이다. 모국어가 제각각이고,
한국어는 대부분 못 하거나 배우는 중이다 ([타깃 사용자](../00-overview/03-target-users.md)).

한국에서 만드는 서비스의 기본값은 한국어지만, 이 서비스에서 그 기본값은 **타깃을 배제**한다.

동시에 개발팀은 한국어를 쓴다. 이 둘이 충돌한다.

## 결정

**층위마다 기준 언어를 다르게 정한다.**

| 층위 | 기준 언어 |
| --- | --- |
| 제품 UI 문구 | **영어** |
| 사용자 콘텐츠 | 작성자가 쓴 언어 그대로 (번역하지 않음) |
| 코드·식별자·커밋 | 영어 |
| **팀 내부 문서 (`docs/`)** | **한국어** |

추가로:
- ~~MVP는 **영어 단일 UI**로 낸다~~ → [ADR-0005](./0005-multilingual-from-day-one.md): 출시 시점부터 다국어.
  문구를 하드코딩하지 않고 **번역 키로** 작성한다는 원칙은 그대로다
- 행정·법률 고유명사는 **영문 + 한국어 원문 병기**를 관례로 한다 (`Alien Registration Card (외국인등록증)`)
- 자동 번역을 전면 도입하지 않는다 — 행정 용어의 오역은 실질적 피해가 된다

## 결과

**좋은 점**
- 타깃 사용자가 첫 화면에서 튕기지 않는다
- 검색 유입이 영어권에서 잡힌다 (주 유입 채널)
- 팀은 한국어로 빠르게 문서를 쓴다

**비용**
- 팀이 UI 문구를 영어로 써야 한다. 영어 UX 라이팅 품질이 문제가 될 수 있다
  → 초기에는 감수하고, 필요하면 검수를 받는다
- 문서(한국어)와 제품(영어)의 용어가 갈라질 수 있다
  → [용어집](../00-overview/05-glossary.md)이 대응표 역할을 한다. 코드/UI는 **영문 용어**를 쓴다
- 한국어 UI를 원하는 사용자(한국인 참여자)에게는 나중까지 불편하다

## 대안

| 대안 | 왜 안 골랐나 |
| --- | --- |
| **한국어 우선, 영어 번역 추가** | 타깃이 첫 화면에서 이탈한다. 순서가 거꾸로다 |
| **처음부터 다국어 (영/한/중/베)** | MVP 비용이 몇 배가 된다. 어느 언어가 필요한지도 아직 모른다 |
| **자동 번역 전면 도입** | 비자·계약 용어의 오역이 곧 피해다. [리스크 정책](../10-domain/10-visa-immigration/03-content-and-risk-policy.md) 위반 |
| 문서도 영어로 통일 | 팀의 문서 작성 속도가 크게 떨어진다. 내부 문서는 외부 노출이 없어 타깃 문제가 없다 |
