# ADR-0011 · 분류는 세 층으로 나눈다 — 네임스페이스는 고정, 값은 개방, 공간은 승격제

- **상태**: 수락됨
- **날짜**: 2026-08-31
- **관련**: [ADR-0008](./0008-nationality-as-tag-not-space.md)의 "태그이지 공간이 아니다"를
  **확장**한다. 0008 은 국적 하나를 다뤘고, 이것은 분류 체계 전체를 다룬다.

## 맥락

**카테고리가 기하급수로 늘어난다**는 전제가 추가됐다. 그런데 지금 태그 문서는
분류를 이렇게 정의하고 있다:

> | **고정 어휘 태그** | `visa:d-2`, `region:seoul`, `school:snu` | **관리자만** |

이 정의는 **값이 적을 때만 성립한다.**

| 축 | 값의 수 | "관리자만" 이 성립하나 |
| --- | ---: | --- |
| `visa:` | ~15 | **된다** — 제도가 정한 목록이다 |
| `topic:` | ~5 | **된다** |
| `lang:` | ~10 | **된다** |
| `region:` | 200+ | 힘들다 |
| `school:` | 400+ | 힘들다 |
| `nationality:` | 190+ | 힘들다 |
| **`company:`** | **수만** | **불가능하다** |

관리자가 회사 이름 수만 개를 미리 입력할 수는 없다. 그런데 값을 사용자에게 열면
`네이버`·`naver`·`NAVER`·`네이버㈜` 가 전부 다른 태그가 되어 **필터가 무너진다** —
고정 어휘를 둔 이유가 바로 그것이었다.

**둘 다 맞다. 그래서 층을 나눠야 한다.**

## 결정

**분류를 세 층으로 나누고, 층마다 다른 규칙을 적용한다.**

| 층 | 개수 | 누가 정하나 | 바뀌는 빈도 | 예 |
| --- | --- | --- | --- | --- |
| **① 네임스페이스** | **적고 고정** (~8) | 코드 + [`contracts/`](../../contracts/README.md) | 거의 없음 | `visa` `topic` `region` `company` |
| **② 값** | **무제한·개방** | 사용자 + 정규화 | 계속 | `company:naver` `region:ansan` |
| **③ 공간(허브 URL)** | **소수·승격제** | **데이터가 정한다** | 자동 | `/companies/naver` |

기하급수로 느는 것은 **② 값**뿐이다. ①은 늘지 않고, ③은 승격 기준이 막는다.

### ① 네임스페이스 — 고정. 늘리는 것이 결정이다

네임스페이스를 추가하려면 FE·BE 코드와 계약 파일을 함께 고쳐야 한다.
그 마찰이 **의도된 것**이다 — 축이 늘어나는 것은 제품 결정이지 사용자 입력이 아니다.

**축이 8개를 넘으면 그건 새 축이 필요한 게 아니라 축을 잘못 나눈 것이다.**

### ② 값 — 개방. 대신 정규화·별칭·병합이 필수다

값은 사용자가 만들 수 있다. 그 대가로 셋을 갖춘다:

| 장치 | 없으면 |
| --- | --- |
| **정규화** (`slugify`, 이미 있음) | `NAVER` 와 `naver` 가 갈라진다 |
| **별칭 사전** (`네이버` → `company:naver`) | 같은 대상이 언어마다 갈라진다 |
| **병합·이관** (관리자) | 오타 값이 값의 수만큼 쌓인다 |

**병합이 없으면 개방한 순간 되돌릴 수 없다.** 값을 열기 전에 병합 기능이 먼저다.

값에 따라 **개방 정도를 달리한다** — 전부 열거나 전부 닫지 않는다:

| 네임스페이스 | 값 정책 | 이유 |
| --- | --- | --- |
| `visa` `topic` `lang` | **닫힘** (고정 목록) | 제도·도메인이 정한 것이다. 사용자가 만들 이유가 없다 |
| `region` `school` `nationality` | **열림, 사전 시드** | 공개 데이터로 미리 채우고 나머지는 제안받는다 |
| `company` | **열림, 제안제** | 미리 채울 수 없다. 첫 사용자가 만들고 관리자가 정리한다 |

### ③ 공간 — 승격제. 데이터가 정한다

[ADR-0008 의 기준](./0008-nationality-as-tag-not-space.md)을 모든 축에 적용한다.

> **주간 신규 10건이 4주 연속 + 답변률 전체 평균 이상**일 때만 값이 허브 URL 을 갖는다.
> 미만이면 필터로만 존재한다.

**허브가 늘어나는 것은 우리가 결정하지 않는다.** 값이 자라면 URL 이 생기고,
말라붙으면 색인에서 빠진다. 사람이 판단하면 기하급수를 못 따라간다.

## 기하급수가 실제로 깨뜨리는 것들

값이 늘면 다음이 순서대로 문제가 된다. 미리 적어 둔다.

**1. 색인 예산.** 허브가 수천 개가 되면 크롤러가 다 돌지 않는다.
→ sitemap 을 축별로 분할하고, 승격 기준 미만은 `noindex` 로 둔다
([라우트·색인](../30-architecture/07-routes-and-indexing.md)).

**2. 탐색 UI.** 게시판 목록으로는 20개까지다. 200개는 못 보여준다.
→ **목록형 네비게이션을 만들지 않는다.** 검색 · 최근 활동 · 내 구독이 진입점이다.
카페식 좌측 메뉴는 이 규모에서 작동하지 않는다.

**3. 빈 값.** 값 하나에 질문 한 건인 상태가 대다수가 된다.
→ 그게 정상이다. 승격 기준이 색인에서 막고, 필터에서는 여전히 유용하다.

**4. 신원 노출.** 축이 늘수록 조합으로 개인이 특정된다.
`company:x` × `visa:e-7` × `region:안산` 이면 몇 명인가?
→ [ADR-0009 의 점검](./0009-nationality-display-policy.md)을 **모든 축의 조합**으로 확장한다.
특히 `company:` 는 **고용주가 볼 수 있다** — 보복 위험이 실재한다.

## 결과

**좋은 점**
- 값이 몇 만 개가 되어도 **코드는 안 바뀐다.** 바뀌는 것은 데이터뿐이다
- 허브 증가가 **자동으로 제어된다.** 사람이 판단하지 않는다
- 축(네임스페이스)이 적게 유지된다 — 늘리는 데 마찰이 있기 때문이다

**비용**
- **병합·별칭 기능이 선행 조건이 된다.** 없이 값을 열면 오타가 영구히 남는다
- 값이 열린 축은 **품질이 사용자에게 달린다.** 고정 어휘의 보장을 일부 포기한다
- 축마다 값 정책이 달라 **설명이 필요하다** — 사용자에게는 그 차이가 안 보여야 한다

## 대안

| 대안 | 왜 안 골랐나 |
| --- | --- |
| 전부 고정 어휘 (지금 문서) | `company:` 수만 개를 관리자가 못 넣는다. 축이 늘면 즉시 막힌다 |
| 전부 자유 태그 | 표기가 갈라져 필터가 무너진다. 매칭 품질이 이 서비스의 가치다 |
| 카테고리(게시판)를 미리 만들어 둠 | 빈 방이 값의 수만큼 생긴다. 커뮤니티로 보이지 않는다 |
| 허브를 사람이 승인 | 기하급수를 사람이 못 따라간다 |

## 열린 질문

- **병합 기능을 언제 만드나?** 값을 여는 것보다 먼저여야 한다 — 순서가 뒤집히면 되돌릴 수 없다
- 별칭 사전을 사용자 제안으로 받을 것인가? (`네이버` → `company:naver`)
- 승격 기준 "주 10건"이 축마다 같아야 하나? `company:` 는 더 낮아도 될 수 있다
- **`company:` 조합의 신원 노출** — 어느 조합부터 위험한가. 실측이 필요하다
