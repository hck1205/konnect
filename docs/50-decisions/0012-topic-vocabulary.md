# ADR-0012 · 주제 어휘를 재편한다 — 비자는 축이고, 재학생은 비타깃이다

- **상태**: 수락됨
- **날짜**: 2026-08-31
- **관련**: [ADR-0007](./0007-settlement-intent-as-primary-axis.md)(정주 의도) ·
  [ADR-0008](./0008-nationality-as-tag-not-space.md)(태그 vs 공간) ·
  [09-content-pillars](../20-product/20-prd/09-content-pillars.md)(비자는 축이다)

## 맥락

게시판을 `topic` 축으로 만들기로 하면서 어휘를 확인했더니 **같은 이름의 두 목록이 달랐다.**

| 어디 | 값 |
| --- | --- |
| `contracts/topics.json` + Prisma `enum Topic`(글마다 필수·단일) | `visa` `language` `education` `housing` `work` `social` |
| ADR-0008 이 추가하기로 한 `topic:` 태그 | `residency` `work` `housing` `admin` `language` |

겹치지도 같지도 않고, [라우트 표](../30-architecture/07-routes-and-indexing.md)가 예로 든
`documents` 는 **어느 쪽에도 없다.**

그리고 실제 어휘에 모순이 둘 있었다.

### 모순 1 — `visa` 가 카테고리로 들어가 있다

[09-content-pillars](../20-product/20-prd/09-content-pillars.md)의 제목이
**"넷이 아니라 하나다 — 비자는 카테고리가 아니라 축이다"** 이고, 본문이 그것을 표로 보인다:

> 집을 계약한다 → 외국인등록증이 있어야 한다 · **체류기간과 계약기간이 어긋나면 계약이 성립하지 않는다**
> 이사한다 → **체류지 변경 신고** 의무가 따라온다
> 정규직으로 옮긴다 → 체류자격이 그 업무를 허용해야 한다

즉 **집·일·행정 모두에 체류자격이 걸린다.** 그런데 `visa` 를 카테고리 값으로 두면
나머지 다섯이 자동으로 **"비자 아닌 것"** 이 된다 — 실제로는 전부 비자와 얽혀 있는데.

게다가 `visa` 는 이미 **태그 네임스페이스**로 존재한다(`visa:f-2`). 같은 개념이
축과 카테고리로 **이중 등록**돼 있었다.

### 모순 2 — `education` 이 비타깃인데 남아 있다

[ADR-0007](./0007-settlement-intent-as-primary-axis.md)이 축을 정주 의도로 바꾸면서
**재학 중인 유학생을 비타깃**으로 내렸다.
[01-visa-types](../10-domain/10-visa-immigration/01-visa-types.md)가 그것을 그대로 적는다 —
"D-2 / D-4 … **재학 중은 비타깃.** 졸업 후 잔류 시점에 다룬다".

그런데 코드에는 `education` 이 1급 카테고리로 남아 있었다.

### 그리고 비치헤드의 집이 없다

`residency`(영주·귀화)가 **어휘에 아예 없었다.** ADR-0007 이 고른 비치헤드가
영주·귀화 준비자인데, 그들의 질문이 갈 카테고리가 없는 상태였다.
`admin`(행정·서류) 도 없어서, [국적별로 답이 진짜 갈리는 것](./0008-nationality-as-tag-not-space.md)
(아포스티유·본국 서류)이 살 자리가 없었다.

## 결정

**주제를 여섯으로 재편한다.**

```
residency   영주·귀화·체류자격     ← 비치헤드의 집
work        일·채용
housing     주거
admin       행정·서류             ← 국적별로 갈리는 것이 모인다
language    어학
social      교류
```

**`visa` 를 뺀다.** 축이지 카테고리가 아니다. `visa:` 태그로만 존재한다.
**`education` 을 뺀다.** 재학 중은 비타깃이고, 졸업 후 잔류는 `residency`·`work` 로 간다.

### 왜 지금인가

`topic` 은 **글마다 필수인 단일 enum** 이다. 값이 바뀌면 Prisma enum 마이그레이션 +
전체 백필 + 계약 + FE·BE 타입 + 사전 4개 국어가 함께 움직인다.

지금 질문이 **3건**이다. 이 창은 닫힌다.

### 기존 데이터 매핑

| 옛 값 | 새 값 | 왜 |
| --- | --- | --- |
| `VISA` | `RESIDENCY` | 그 값으로 분류된 글이 F-2-7 점수 질문이었다 — 체류자격 질문이다 |
| `EDUCATION` | `RESIDENCY` | 유학 글이 남아 있다면 졸업 후 잔류 맥락이다 |
| 나머지 | 그대로 | |

마이그레이션 SQL 의 `USING` 절에 이 매핑이 명시돼 있다. **없으면 기존 행이 전부 실패한다.**
적용 후 확인: `LANGUAGE 1 · HOUSING 1 · RESIDENCY 1` — 손실 없음.

## 대가

**`docs/10-domain/` 과의 1:1 대응이 깨진다.** 스키마 주석이 "docs/10-domain 의 6영역과
대응한다"고 적고 있었고 실제로 6개 디렉터리와 1:1 이었다.

디렉터리를 재구성하지 **않는다.** 도메인 문서는 *지식을 주제별로 묶은 것*이고
`topic` enum 은 *글을 분류하는 축*이라 목적이 다르다. 억지로 맞추면 도메인 지식이
제품 결정에 끌려다닌다. 대신 **주석에서 1:1 주장을 뺀다** — 틀린 주장을 남기는 것이
더 나쁘다.

`30-education` 문서는 그대로 둔다. 재학생이 비타깃이라는 것은 *우선순위*이지
*그 지식이 틀렸다*는 뜻이 아니다.

## 하지 않은 것

**`documents` 를 topic 값으로 만들지 않는다.** `admin` 안에 넣는다.
값을 하나 더 늘리는 것보다 `admin` 하위 앵커(`#nationality-vn`)로 두는 편이
[ADR-0011](./0011-taxonomy-that-scales.md)의 "축이 8개를 넘으면 축을 잘못 나눈 것" 원칙에 맞고,
[깊은 페이지 하나가 얕은 페이지 190개보다 낫다](../30-architecture/07-routes-and-indexing.md)와도 맞다.

**ADR-0008 의 `topic:` 태그를 별도로 만들지 않는다.** 글의 `topic` enum 이 그 역할을
이미 한다. 같은 것을 두 번 두면 다시 갈라진다 — 이 ADR 이 고치려는 것이 정확히 그 상태다.

## 열린 질문

- `residency` 와 `admin` 의 경계. "체류지 변경 신고"는 어느 쪽인가?
  지금 답은 **행위가 서류 제출이면 `admin`, 자격에 대한 질문이면 `residency`** 인데
  실제 글이 쌓이면 흐려질 것이다
- 재학생 질문이 실제로 들어오면 어디로 보낼 것인가. 지금은 `residency`·`work` 로
  흡수되는데, 유학 관련 유입이 유의미해지면 비타깃 결정 자체를 다시 봐야 한다
