# 공감 표시 (리액션)

> 우선순위 **P1** · [핵심 기능](../02-core-features.md)

## 목적

어떤 답이 실제로 도움이 됐는지 드러낸다.

채택 답변(질문자 1인)만으로는 부족하다 — 질문자가 사라진 오래된 질문에도
좋은 답이 달리고, 여러 답이 각각 다른 상황에 유용한 경우가 많다.

투표(upvote)보다 리액션을 고른 이유: **부담이 적다.** "추천/비추천"은 평가처럼
느껴져 참여가 줄고, 특히 자기 답이 비추천당할까 걱정하는 신규 사용자를 위축시킨다.

## 종류 — 고정 어휘

| 코드 | 이모지 | 뜻 |
| --- | --- | --- |
| `like` | 👍 | 좋아요 |
| `helpful` | 💡 | 도움돼요 |
| `support` | 🤝 | 응원해요 |
| `celebrate` | 🎉 | 축하해요 |
| `insightful` | 👀 | 유익해요 |

**임의 이모지를 허용하지 않는다.** 이유:

- 같은 뜻의 이모지가 수십 개면 집계가 무의미해진다
- 이모지는 **문화권마다 뜻이 다르다.** 다국적 사용자를 대상으로 하는 서비스에서
  특히 위험하다 — 어떤 손 모양은 일부 지역에서 모욕이다
- 모더레이션 대상이 늘어난다

## 규칙

- **한 사람이 하나만** 고른다. 다른 것을 누르면 갈아탄다.
  여러 개를 허용하면 "이 답이 도움이 됐나"를 세는 의미가 흐려진다
- 자기 글에도 누를 수 있다(막을 이유가 없고, 막으면 구현만 복잡해진다)
- 비회원은 **보이지만 누를 수 없다** — 읽기는 공개다
- 개수가 0인 종류는 표시하지 않는다. 회색 아이콘을 늘어놓으면 실제로 눌린 것이 안 보인다

## 접근성

이모지 옆에 **번역된 이름**이 함께 읽힌다(`sr-only`).

- 이모지만으로는 의미가 전달되지 않는다
- 스크린리더가 이모지를 제조사·플랫폼별로 다르게 읽는다
- 색·모양만으로 상태를 전달하지 않는다는 원칙과 같은 맥락
  → [접근성](../../25-design/10-foundations/07-accessibility.md)

## 구현

`FE/src/components/community/ReactionBar/` — 토글 로직은 순수 함수라 낙관적
업데이트에 그대로 쓸 수 있다(`toggleReaction`, 테스트됨).

동수일 때 `REACTION_KINDS` 순서를 지킨다 — 정렬이 불안정하면 리렌더마다
순서가 바뀌어 화면이 흔들린다.

## 열린 질문

- 리액션을 **평판**에 반영할 것인가? 반영하면 리액션 구걸(reaction farming)이 생긴다
- 누가 눌렀는지 목록을 보여줄 것인가? 사생활과 사회적 압박 문제가 있다
- 채택 답변과 리액션이 **엇갈릴 때** 정렬을 어떻게 할 것인가?
